# 运行中插入用户引导消息：实施规则

日期：2026-10-13。状态：**已批准，已实施**。回归和安装实例证据保存在对应任务的运行记录与资源索引中；本文件只保留长期有效的实施规则。

本方案替代上一轮 A 的业务范围台账方案。本轮已批准的 Skill 发布覆盖独立实施。

## 1. 目标与改动前基础

用户在任务尚未结束时输入一句话，正在运行的主 Agent、Browser、Reviewer 能及时使用这条信息重新判断。消息可以补充要求、纠正方向、提出问题；不要求用户先终止任务再 `/resume`。

下面是改动前的缺口；本轮在这些位置接入了同一任务输入源：

- `harness/_vendor/tau_agent/harness.py` 已有 `steer()`、steering 队列和 follow-up 队列。
- `harness/runtime/agent_loop.py` 在函数内部持有 Tau 实例，尚未接入终端的任务消息。
- Tau 目前在一轮工具批次之后取 steering，可信终止工具可以直接结束。因此仅调用 `steer()` 不足以阻止同批后续工具或结束竞态。
- `harness/runtime/hitl_input.py` 已有单一 stdin broker、问题编号和提醒，但只在等待 HITL 时注册读取；不是运行期间持续输入。
- Browser 使用自己的执行循环；Reviewer 使用单独循环，不自动消费 Tau 队列。
- `harness/planning/context.py` 已有可持久化的 `operator_inputs`。Reviewer 提交时也检查用户输入有没有变化，目前变化后返回 unavailable，尚不能自然继续审查。
- Workflow 连续执行器按 `continueWhen` 自动进入后续阶段，目前没有用户消息边界。

实现应扩展这些位置，不新增编排 Agent，也不把各个模型循环全量重写成同一实现。

## 2. 用户输入规则

第一版开放 steering，暂不增加 follow-up 等第二套延迟队列。

| 输入 | 行为 |
| --- | --- |
| 普通文本，或 `/guide <文本>` | 引导当前整个任务；进入下一可控边界，重新判断方向 |
| `/answer <问题编号> <回答>` | 回答已显示的 HITL 或授权问题，保留问题归属 |
| `/messages` | 查看已接收消息、各角色接收状态和待回答问题；无需模型调用 |
| `/pause` | 停止派发新动作，请求在途 Workflow 暂停；保持进程和任务，不等同于完成 |
| `/continue` | 在收到暂停确认并核对在途效果后恢复；若仍有必需授权/HITL，不绕过它 |
| Ctrl+C | 沿用现有取消/保存机制；不改造成含义不明的“撤销上一步” |

**任务运行期间普通文本始终作为引导，即使当前有 HITL 问题。** 回答问题统一使用 `/answer`，避免“尺寸还没填”被错误当作价格问题的答案，或“继续”被当成授权。没有任务输入所有者的独立 HITL 调用保留原回答方式。

- 空行忽略；未知斜杠命令提示用法，不能悄悄当成业务指令。
- POSIX 终端支持退格、左右移动、Home/End、历史及 bracketed paste。多行粘贴保留原文，按 Enter 后提交；快速连续输入行在约 100ms 的提交窗口内合并。EOF/Ctrl+C/结束时恢复终端设置。
- 不在任务运行期间解释 `/skill-create`、`/browser` 等为另开任务；结束当前任务后再进入模式命令。
- 不消费非交互 stdin 中原有的管道任务输入。本阶段只接交互终端，不额外开放远程消息端口。

## 3. 消息的含义和权限

原始目标保持不变，新输入以真实用户补充的身份追加。模型结合原目标和全部补充判断哪些要求改变、哪些继续有效；Harness 不用关键词推断“这是尺寸要求”或“此消息优先于价格”。

- 同一用户后来的明确修正可覆盖其先前要求；未涉及的要求继续有效。
- 冲突或含糊之处交由模型决定是否需要 HITL；不能把全部历史要求用最后一句话替换。
- 用户询问进度时，模型简短回答后继续原任务；用户明确停止、缩小范围时遵守新范围。
- 输入是一条引导，**不自动成为路径授权、提交上架许可或新的页面租约**。已有授权流程仍按对应问题和范围处理。
- 文件、网页、工具输出、子 Agent 总结不能伪装成该入口的用户消息。
- 本方案不保证用户不干预时模型永不遗漏；它解决的是用户观察到问题后无法及时纠正。现有完成审查继续保留。

## 4. 保存、顺序和反馈

复用 task control 的用户输入记录，新增必要的顺序和消费字段，不建立重复的业务要求台账：

```text
inputId / taskId / sequence / receivedAt / source=terminal_steering / text
每个角色：deliveredThrough / acknowledgedThrough
任务：inputRevision / finalizingRevision
```

- 先成功落盘，再显示“已接收”。失败时明确显示未接收，不能只放进内存队列。
- 单任务单写入者分配顺序。异步角色只能推进各自消费位置，不能用旧会话状态覆盖新输入。
- 保留每条原文；同一边界前收到的消息可打包进入一次模型请求，但不做语义合并或改写。
- 同一角色已处理的消息不重复插入；退出恢复时，尚未消费的消息仍然存在。
- “已接收”表示已持久化；“已送达”表示已进入该角色的上下文；“已回应”表示该角色已针对包含这一批输入的请求返回完整模型回复。三者都不表示对应业务动作已经完成，模型错误或截断不会被标成回应。

示例：

```text
[用户引导 #18 · 已接收] 尺寸规格还没有填写，请按商品信息.md补齐。
[执行状态] 当前上传仍在途；已停止派发下一阶段。
[用户引导 #18 · 已送达] Workflow 主 Agent、Browser-003、Reviewer
[Workflow] 将核对规格编辑区，补齐尺寸和颜色，再核对生成行的库存价格。
```

终端继续显示待回答 HITL，保留现有时间/消息数量提醒。引导的接收状态不混入模型普通日志，用户不必翻阅多个 Agent 的长输出寻找确认。

## 5. 谁收到消息

采用**同任务共享原始输入，各角色独立消费**。不让用户猜当前哪个 Agent 才是接收者。

| 角色 | 收到后的职责 |
| --- | --- |
| Workflow / Skill 主 Agent | 解释补充要求、核对已发生效果、调整剩余计划/输入，或回答用户问题 |
| 独立 Browser 主 Agent | 在当前 Browser 循环内重新判断目标和后续动作 |
| 被委派的 Browser | 获得原始消息；在原委派权限内调整。涉及委派目标、页绑定或权限变化时交回主 Agent，不自行扩大范围 |
| Reviewer | 以新用户上下文审查；可以延续已有事实和问题，但旧目标下的“完成”结论不能直接结束任务 |
| `/skill-create`、`/skill-edit` 的作者循环 | 使用同一入口调整当前草稿和验证目标，保持发布仍由用户命令执行 |
| Workflow 的 JS/TS 程序 | 不接收自然语言。暂停/收回执后，由主 Agent决定续跑原实例，或调整输入/程序后启动新的有界调用 |

- 已结束的 Browser 不因消息广播重新启动；后续被委派时获得最新用户上下文。
- Reviewer 的只读身份不变。用户说“把规格填上”，Reviewer 应指出待完成工作并交回执行者，不获得页面写权限。
- 主 Agent 等待 Browser 或 Reviewer 时，输入 broker 仍可接收消息，并直接通知这些正在运行的角色；不必等主 Agent 的委派调用返回才转达。
- 第一版不做 `/guide @worker`：业务目标属于整个任务，局部私信容易造成主 Agent、执行者和审查者认识不一致。

## 6. 消息何时生效

原则：**立即接收；阻止尚未派发的旧决策；在途操作保存真实结果。**

| 消息到达时机 | 处理规则 |
| --- | --- |
| 下一次模型请求之前 | 注入未消费输入，再发模型请求 |
| 模型正在生成 | 不把新消息硬塞入已经发出的请求。返回后先检查输入序号；旧回复中的未派发工具不执行，补齐未执行的工具结果，再带新输入重新判断 |
| 同一模型回复有多个工具 | 每个工具派发前检查。消息到达后，尚未派发的工具以 `not_executed: user_input_pending` 记录；在途工具收回执 |
| 原生 Browser 动作已经发出 | 不能撤回已点击、已上传的事实。等回执或确认未知状态，再注入消息；不能凭取消 await 判断浏览器没执行 |
| 多阶段 Workflow 连跑 | 当前阶段返回后，先处理消息，再判断是否进入下一阶段；即使原 `continueWhen` 满足，也先让回模型 |
| Reviewer 正在审查 | 将新输入送入下一审查轮；保留仍有效证据。提交时检查目标修订号，拒绝以旧目标完成收尾 |
| HITL / 授权等待中 | 持续接收引导，但引导不自动解答问题。模型可以因新范围撤回过期业务问题；权限请求只能由原授权机制处理 |

第一版不为节省一次旧模型输出而强行取消所有 provider 请求；先保证请求/回复归档、工具配对和计费记录正确。可取消 provider 的优化应另以实际供应商行为验证。

### 长时间 Workflow 的特殊边界

安装实例已验证 `pausing → paused → running → succeeded`。`Workflow.pause` 在异步作业边界暂停，不能任意停止某条 JS 指令。原 execute 请求在暂停时仍未返回；Harness 保留此请求，确认暂停后交回模型，而完整结果另行落盘。

1. 输入到达后，Harness 先关闭后续派发；已有 workflowId 时请求 `Workflow.pause`。
2. 返回 `pausing` 只表示请求中；确认 `paused` 才表示平台暂停。执行已完成则正常收尾，不伪造暂停。
3. workflowId 尚未可用时监听实际事件/回执；向终端说明仍有在途操作。不能猜 ID 或取消连接冒充取消执行。
4. 暂停等待不能阻塞 stdin 和状态显示。状态未知时停止后续写操作，保留原始证据进行诊断。
5. 新指令不影响已绑定程序剩余动作时，模型可以选择恢复原实例。新指令要求改变剩余输入/源码时，不能直接修改运行中的 JS；根据现有输出和页面事实选择结束旧实例、核对副作用，再调用修订后的程序。
6. 若 WebCross 的暂停或观测不符合协议，定位并反馈平台问题。Harness 不能用反复取消/重试或 Runtime.evaluate 绕行掩盖它。

实施接口 `control_workflow_execution(workflow_id, action)` 只接受该任务已记录的执行 ID，检查 Fleet 和控制能力；原始结果通过 `resultRef` 读取。再次恢复之后，后续引导仍能触发暂停。暂停能力不可用或请求失败时返回明确的 `unknown / pauseConfirmed=false`，保留在途请求，不能宣称它停止了。

任务内还有运行、暂停或未知状态的 Workflow 时，Browser 页面交接先返回 `execution_control_required`。这是已有页面所有权和在途执行状态的边界：避免关闭原连接后丢失请求、或让第二个写入者与原程序争用页面。只读审查及原执行服务的观察仍可用。恢复路径为查询、恢复或取消原执行，核对原回执后再交接；不依据站点、字段或业务路径决定。结束时取消本任务仍在途的作业并保存实际回执；取消未确认就保留 `uncertain`。

因此，普通引导能够及时阻止下一批动作，但不承诺撤销任何已经发生的副作用。

## 7. Reviewer 与结束竞态

本例最重要的场景是：用户在 Reviewer 准备判定完成时说“尺寸没有填”。

1. 输入落盘令 `inputRevision` 增加。
2. Reviewer 获得原文，重新判断缺口；无需丢弃之前核验过的图片和价格事实。
3. 原审查若返回了基于旧修订号的 `complete`，保留为历史结果，不能提交任务结束。
4. 主 Agent 获得新输入和待处理事实，完成必要调整，再审查。
5. 最终完成提交与消息接收共享一个短临界区：所有已确认接收的引导均已由任务拥有者处理，且最终审查绑定当前输入修订号，才能写入终态。

这是一条**目标身份一致性检查**，不是“尺寸必须填写”的业务门禁。它适用于任何目标变更；可能多触发一次没有实质变化的审查，恢复方式是在新目标修订下复用有效证据并重新提交。不能交给模型自行决定是否忽略这个竞态，因为输入可能在模型请求发出后才到达。

已写入终态后到达的文本不能自动交给下一任务：明确显示“本任务已结束，未插入；可用 /resume …”。仍在编辑的文本会显示为未提交草稿，供用户复制后重新发送；清理旧读取者和输入队列，防止成为下一任务的命令。不要先显示“已接收”再默默丢弃。

## 8. 恢复与权限边界

- 中断后 `/resume` 恢复输入原文、消费位置、待回答问题和执行检查点。已消费输入不再次冒充新指令；仍进入必要的持久用户上下文。
- 消息送达 Browser 不等于主 Agent 已处理；各角色独立记录，避免一个角色先消费后其它角色看不到。
- 用户改变方向不清空已完成效果、不从首页重跑，不触发新的 Builder 子 Agent。
- 新消息没有变更用户授权的文件/页面范围。扩展访问范围继续按现有授权和页租约处理。
- stdout 接收确认避免打印敏感长文本；持久化沿用现有输入与日志脱敏规则，不能把秘密写进 system prompt。
- 多页面和多个角色共享目标变化，不共享页面控制权。恢复页面仍由当前租约持有者执行。

## 9. 实施与验收

以下步骤已接入：

1. **终端入口与持久输入**：将 HITL broker 扩为任务全生命周期单 stdin 所有者；增加引导、显式回答、查询状态和多行粘贴。任务结束后清理读取者，避免偷走下一条模式命令。
2. **主循环与委派接入**：接 Tau、Browser 和连续 Workflow 派发边界；保留工具调用/结果配对。通过同一任务输入源给活动 Browser 送达消息。
3. **Reviewer 与结束一致性**：新输入触发继续审查而非无限 unavailable；保留证据/问题，终态按当前目标修订提交。同步覆盖 `/skill`、Workflow 和独立 Browser。
4. **WebCross 暂停验证及接入**：分别验证运行、暂停请求中、暂停成功、自然完成、失联这些状态。工作区协议与安装实例版本分开记录。
5. **恢复与回归**：包括消息恰好到达工具边界、连续发送三条、HITL 同时存在、委派未返回、Reviewer 结束竞态、断线恢复、EOF 和 Ctrl+C。

实现位置：`harness/runtime/{steering,terminal_editor,hitl_input,agent_loop,workflow_steering}.py`，Browser 与 Reviewer 循环、Skill/Workflow 连跑边界及 Builder 入口。没有消息时不增加模型调用，不扩写 system prompt；输入、角色消费位置和作业身份保存在现有 task state 中，接受新计划时保留这些事实。

真实测试使用无页面动作的纯 sleep Workflow，覆盖暂停、二次引导、恢复、任务退出时取消和完整结果保存；另一个 Agent 身份没有收到该执行事件。新 Fleet 的 `Page.create` 在 about:blank 与本地 HTTP 测试页上均返回初始加载失败，因此本轮没有完成真实表单写入回归。该失败来自直接平台调用，未进入 Harness 页面动作策略，未用重试或 Runtime.evaluate 掩盖。不要将本次结果解释为完整商家任务或性能评测。

验收例：

- 本案例输入“尺寸规格还没有填写，按商品信息.md补齐”，主 Agent 核对资料和页面后调整工作；Reviewer 不沿用旧“已完成”结论。
- 在库存填写中输入“价格先别改”，尚未派发的改价停止；已执行的写入明确报告，不声称回滚。
- 询问“现在做到哪里”，简短回答后继续原任务，不丢弃未完成目标。
- 有价格 HITL 时输入规格引导，两条信息不混淆；价格仍需 `/answer`。
- 无消息的任务不增加模型调用，不轮询 LLM。消息批量送达产生必要的重新判断；数据查询、排队确认、提醒由 Harness 完成。

性能评估同时记录引导接收延迟、送达延迟、模型调用数、cache_read / cache_creation / uncached_input / output、平台 I/O、失败重试，以及排除人工等待后的总耗时。不能只以“消息更快进入上下文”宣称整个任务更快或更便宜。
