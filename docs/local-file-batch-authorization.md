# 本地文件批量与目录授权

## 问题证据

任务 `1e7de846aa2143feadddf40aa33175d3` 的持久化模型回执显示，GLM-5.3
一次调用 `authorize_trial_files`，传入十张图片。旧 Builder 在同一次工具调用中
逐项调用 `authorize_path`，因此产生十次独立确认。五个已批准记录均为单文件，
并没有被遗失的目录权限。来源任务 `97c1f972c9744351b0ae424d9683a722`
曾申请并获批整个商品目录；来源任务使用 Browser 角色，本次使用 Skill Builder。
这些不同入口的结果不能作为模型能力的受控比较。

确认发生在 Harness 本地，尚未到 WebCross 上传。核查时运行进程为当前仓库
`main.py`，启动记录 `1653c4a-dirty.8a3e571e7fac`；修改工作区不会更新它已加载的模块。

## 统一行为

- `local_fs_authorize(paths, mode)` 在 Browser、Workflow、Skill、Builder 提供同一合同。
  不读取或修改文件内容，只请求权限并返回实际获批范围。`mode` 默认 `read`。
- 旧 Builder 的 `authorize_trial_files` 保留为 READ 入口，复用同一实现。
- 一批相同权限的路径一次确认。`yes` 只批准显示的请求范围；`no` 拒绝整批尚未批准的范围。
  已获批路径不重复询问。读写混合操作分别确认 READ 与 WRITE。
- 如果存在可用的共同目录，界面显示它的确切路径；用户可选择 `directory`。
  这是客观路径关系产生的可选项，不能自动变成授权或模型的业务选择。
- 模型按原始目标选择材料/交付目录，目录授权覆盖同一任务、同一权限下的后代。
  单文件的普通 `yes` 不会批准父目录或兄弟文件。
- Workflow 的授权落到任务所有者，而非独立 Coding 工作区。所属试运行与恢复沿用
  现有主机验证的归属关系，复制确切 READ 范围，不复制 WRITE，不扩展到无关任务。
- Workflow 上传仍校验实际输入文件清单。目录获批不会自动枚举或上传整棵目录。

## 边界和恢复

所有原始路径在确认前检查，并在人工等待后重新解析。受保护路径、任务控制区写入、
符号链接目标变化、权限模式和已有拒绝属于客观权限边界；同批包含不合法路径时不执行工具。
目录候选不能覆盖先前拒绝的范围，试运行权限继承也不能覆盖该试运行已有的拒绝。
这些校验适用于所有站点和文件类型，不添加业务路径、选择器或字段特判。
目录选择会扩大可访问范围，因此必须由终端明确选择，LLM 的申请本身不构成批准。

EOF、取消与无法识别的输入均不授予权限。无效回答保留完整范围和选项重新询问；
取消释放本任务的授权等待屏障。范围问题可通过修正路径重新申请；已拒绝范围不能改用父目录绕过。
批准记录沿用现有独立权限文件格式，恢复任务可读取旧的单文件或目录记录。
请求与批准事件携带 `authorizationId`，便于区分一个批次的多个路径和多次人工确认。

旧进程仍在等待时需要退出并重启 Harness，再执行 `/resume <任务ID>`。
已有单文件批准会复用；新进程可将剩余文件一次确认，或按任务目标明确申请完整材料目录。
本次修复不通过直接修改原任务权限记录或替用户回答授权问题来使旧进程继续。

## 验证范围

`test_local_access_batch.py` 覆盖十文件批量、目录选择、旧批准复用、跨任务和读写隔离、
受保护成员、等待期间符号链接变化、EOF、拒绝、并发、取消和声明目录预检。
`test_local_access_profiles.py` 调用各入口的真实工具回调，验证授权归属、持久化恢复、
Workflow 所属试运行/恢复及 Builder 上传前的批量确认；平台调用使用测试替身。
这些验证不构成真实站点上传或模型 token、耗时改善的实测结论。

相关回归最终为 153 项通过、11 个子测试通过。额外运行的 `test_workflow_policy.py`
有 13 项失败、10 项通过；在隔离副本恢复本次修改前的模块后，同样复现这 13 项失败，
原因是旧 steps DSL 测试依赖的 `waitEvent/readEvents` 等合同不在当前源包 schema 中。
本次不修改这些协议测试或平台缓存。命令范围、源码哈希和运行实例状态见
具体回归回执保存在对应任务的运行记录与资源索引中；本文件只保留长期有效的授权规则。
