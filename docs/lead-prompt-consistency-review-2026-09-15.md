# Lead prompt 一致性整理与审阅记录

本轮针对已确认的提示词矛盾、阶段混杂和重复派发参数做整理。修改仅涉及 Lead 提示词、工具描述、guide 及相关测试；没有改调度算法、合同校验规则、URL 解析、模型配置，也没有运行真实模型任务。

## P0：统一后的规则

| 场景 | 统一指导 |
| --- | --- |
| 计划获批 | 执行已批准计划，不重新生成同一计划。修订确有必要时仍走原审计、批准路径。 |
| 自动调度 | Lead 声明 phase 和依赖；Harness 可以派发已批准的 ready phase、自动补位和有界续跑，不发明业务 phase。 |
| 并发 | max_browser_agents 是运行 worker 的上限；有效槽位容量至少为该值，不用更小的原始槽位配置再次压低并发。 |
| 页面与槽位 | 有实际页面连续性需求才传页面复用参数。reuse_from_worker_id / preferred_slot_id 固定槽位，可能使工作串行；同一可变页面也可能串行。 |
| 字段为空 | required 表示输出键必须存在；非空和带证据为空按原始目标决定。禁止一律非空或一律允许缺失，执行阶段不得擅自放宽已批准合同。 |
| 内部异常 | tool_exception 不证明某个合同字段非法。遵守 replayForbidden，读取能回答具体疑问的证据，不用改计划或试验性 spawn 猜测内部故障。 |
| 部分完成 | partial 本身不强制重试或重规划。先读自动续跑回执，再根据剩余义务、证据、预算及身份约束判断。 |

## 阶段与内容归属

- 规划 prompt 保留任务分解、输入来源、合同语法、数量与空值语义、能力边界、并行依赖和审计修复。
- 执行 prompt 从已有批准计划开始，保留派发、事件等待、结果解释、续跑、必要重规划、身份连续性和结束标准。
- 嵌套集合写法、原生图片导出与文件下载的选择、content_completeness 的边界移入 lead.plan-contracts。
- 空值和数量的细节归 lead.artifact-validation；批次检查点归 lead.cohort-checkpoints；身份与页面恢复归 lead.fleet-session-continuity。
- spawn 默认示例只传 phase_id。task、context、result_contract、worker_contract 是有具体需要时使用的补充，不再要求模型重复复制整个合同。
- 删除默认“同站点并发必须加延迟”和“所有详情任务必须先走源卡片”的通用命令。保留用户时序要求、真实共享状态约束、观察到的源 URL 和 verbatim href；具体路线由模型根据事实选择。

## 本地验证

262 项相关测试通过，包括 guide 注册与检索、few-shot 工具 schema/计划编译、规划修复、槽位调度、合同继承、认证中断边界。编译检查与 git diff --check 通过。

新增行为检查确认：只传 phase_id 的实际 Lead 工具处理路径，将批准的 worker_task、expected_artifact 和 validators 传给 spawner。测试截断在 spawner 边界，不连接浏览器或调用模型。

部分旧测试要求执行 prompt 必须含完整嵌套字段例子或“源卡片是默认路径”等旧文案，现改为检查对应 guide 的可达性、工具说明与 prompt 的一致性及实际能力边界。

| --- | ---: | ---: | ---: |
| 执行 | 34,446 | 11,386 | -66.9% |
| 规划 | 9,806 | 10,883 | +11.0% |

不同运行配置、guide 描述、部署追加指令及任务静态上下文会影响最终体积。上述数据不包含工具 schema 或对话历史；尚未测量真实模型的首轮通过率、总 token 或耗时收益。

## 下一轮真实任务观察项

1. 首份合同是否通过；驳回后是否针对具体字段修复。
2. 批准后是否重复 emit 或无依据改计划。
3. 普通 spawn 是否以 phase_id 为主，以及并行 phase 是否按批准依赖派发。
4. tool_exception 后是否继续无信息增益的重复检索、变参重放。
5. 分别统计规划与执行调用耗时、输入/缓存/输出 token，并剔除人工等待。

真实任务应使用重新启动或已重新加载修改的 Harness 进程。此轮仍未修复此前离线复现的 URL 提取异常；提示词改进不构成该异常已消失的证据。
