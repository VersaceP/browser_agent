## 三、空值合同存在三层不一致，已离线复现

### 1. 声明允许，编译后许可丢失

`task_plan.json` 中：

```json
{"name":"filledValue","type":"string","allow_empty_with_outcome":["confirmed_absent"]}
```

但最终两个 `field_nonempty` validator 都没有 `allow_empty_with_outcome`。

- `harness/task_control/validators.py:1461` 优先取 `required_fields`；本例它只是字段名列表。
- `:1665` 的许可解析只查传入列表中的对象或顶层映射，没有回查 `fields` 中的字段定义。
- `:1488` 的 `requiredControls` 分支又生成一条无条件的 `controlKey/filledValue` 非空规则。

同一解析函数的离线结果：传入本任务 `required_fields` 得到 `{}`；传入 `fields` 得到 `{"filledValue":["confirmed_absent"]}`。两个实际非空 validator 对价格/库存行均失败。

### 2. 证据字段声明成 string，运行时只接受 object

计划将 `filledValueAbsence` 声明为 string。`harness/results/row_ledger.py:92` 接受对象形式的 outcome/evidenceText（或已有的同级协议字段），不解析任意 JSON 字符串。

- 首次工件 `0268a8ca` 用字符串：类型符合合同，absence 协议不接受。
- 第二次 `49eef9ae` 改用对象：absence 解析接受，但 `current_row_structure_failures` 判它违反 string 类型。
- 非空许可丢失仍独立存在，换格式也不能修好。

Worker 因而在步骤 15、16、18、19、20 保存了五份完整七行回执。修复段约 91 秒；没有创造新的页面业务进展。

这类反复出现的冲突需要在协议边界修复，不能继续让 Worker 试换字符串/对象。当前 `harness/evidence/extraction_artifacts.py` 的 `resolve_required_field_specs` 会回查被引用的字段定义，空值许可编译却采用另一路解析，证据读取再独立约定可接受的结构。应统一字段引用解析、明确支持的证据表示及其绑定方式，使计划编译、工具说明、行类型检查和证据消费使用一致定义。对于选定协议与声明类型的客观冲突，应在计划接纳前返回具体冲突路径和受支持表示。不得仅凭字段后缀将任意业务字段判作协议字段，也不得把所有 JSON 字符串自动解析成对象。历史上已经支持的同级 outcome/evidenceText 表示应明确保留或提供显式迁移。

### 3. 返回的失败可能属于旧候选，而非刚提交的工件

`artifact_validation.py` 选择结构较好、行数较多、较新的可用候选。对象版本有类型错误，于是回退到旧字符串版本。`record_extraction` 返回的新 `savedPath` 与 `artifactValidation.artifacts` 指向不同文件，模型仍看到旧的 `declarationAccepted=false`。

候选回退有合理用途，不能简单改成“永远选最新”。工具应同时返回“本次提交为何失败”和“当前选中交付版本及原因”，让模型停止猜测。

另外，资料缺价格、用户尚未答复，与“商品无需价格”含义不同。格式修复不能把业务阻塞自动变成成功；允许记录事实与完成用户目标必须分别判断。

这些修复涉及通用消息不丢失、合同一致性、事件身份和只读状态边界。不会新增依据站点、字段名或猜测业务意图的门禁。字段是否应填、目录是否同一商品、缺失资料是否仍允许继续，都继续由模型结合原始目标和用户补充判断。

### 机械校验的边界与恢复

- 普适性：仅检查显式选定协议能否被一致消费、消息及审批是否绑定正确对象、操作是否超出已有权限。这些条件与商品、站点和业务字段含义无关。
- 误杀面：历史合法表示或仅名称相似的业务字段可能被错误拒绝。因此校验限定于已明确参与协议的结构，保留受支持表示，并通过字段改名及表示等价测试验证；不能从字段名称猜测业务要求。
- 恢复路径：返回冲突的原始声明、具体路径、期望结构、当前候选身份及受支持表示，允许模型局部修复或重规划；用户输入和原始工件保留，修复不会抹去已发生的执行事实。
- 为什么不能只由 LLM 判断：相同合同在不同执行层必须具有同一确定含义，权限和身份绑定也不能随模型判断漂移。LLM 决定应采用什么业务合同及证据是否足以支撑业务结论，机械层只验证选定合同的结构、一致性及执行权限。

本次未完成仍有未解决的资料与来源问题。是否需要补充哪些业务信息、是否可以继续，由模型结合页面证据和用户目标判断；协议修复本身不能补出缺失数值或替用户决定业务来源。

## 八、批准后的实现与验证

### 已落地的通用 Harness 改动

1. 计划审批每条输入先写 `task_plan.approval_input_received`，随后写分类结果及错误码。输入带 `inputId`、候选哈希和时间。分类失败后用户再说“确定”不会静默丢弃先前补充，而是要求修订；正常分类为含糊的意见后明确确认，保留原话交给 Lead，不机械强制重规划。
2. 执行阶段交接保留审批输入的原文、候选身份和分类来源。恢复时从当前配置的事件存储读取计划审批与 HITL 原文，向 Lead 提供有界的近期回执及完整事件来源。旧意见是历史证据，不自动变成新权限或业务完成结论。
3. HITL 回复带 `feedbackId`、`pageId`、`pauseId`、请求目的和协助类型写入事件，再进入 Worker 下一轮模型请求；若上下文压缩移除了这段尚未处理的原文，下一轮请求会补回。业务询问不再靠“登录”等关键词启用浏览器挑战恢复；已观察到的结构挑战仍可触发其恢复流程。
4. 必填字段引用、显式非空与条件空值许可共用字段声明解析。行类型错误指向具体 JSON Pointer。已有的同级 `Outcome`/`EvidenceText` 表示继续受支持，所以 `Absence` 声明为 string 本身并非必然不可能；把对象硬填进 string 字段或把 JSON 对象编码成字符串仍会得到明确诊断。没有新增价格、库存、站点或选择器特判。
5. 工件验证回执同时显示本次提交与当前选中候选的路径及失败。暂停/超时状态下允许只读 `inspect`，`accept` 仍遵守原状态门。direct Worker 完成事件与普通 wait 共用消费记录，普通 wait 不再把已消费完成项作为新结果交付。计划修复失败给出与实际候选匹配的 JSON Pointer；Lead 可按范围决定局部修复或整体重规划。

这些是工作区源码修改，尚未部署到既有运行实例；没有修改 WebCross 代码。旧任务 `0eb91e0` 的缺失业务资料也没有通过代码补齐。

### 数字核验的离线评估

原任务报告 2,540 字符、35 个数字片段；按段落将其分成 5 组时，片段数为 3、7、9、8、8。原运行的一次提取加一次完整修复共用 7,442 uncached_input、28,566 output token，耗时 524.670 秒，仍有 8 个片段未覆盖。分组可能缩小单次输出和修复范围，但重复上下文、更多模型轮次和平台 I/O 也可能抵消收益。

本次尝试对这 5 组用相同模型做离线对照；5 组均未获得有效提取结果，合计等待约 180.66 秒。随后以短超时探测得到 `LLMConnectionError: qwen-token-plan.responses.stream lost the connection (APIConnectionError)`，不能据此判断分组方案的正确性、token 或有效净耗时。因此没有把分组方案切入生产路径，也没有降低数字覆盖与矛盾校验。待模型连接可用时，需对相同报告比较 cache_read、cache_creation、uncached_input、output、调用轮次、平台 I/O、覆盖和排除人工等待后的耗时。

### 回归

采用与站点及业务字段无关的样例覆盖审批连续输入、恢复回执、HITL 请求绑定、字段引用和空值协议、工件回退、只读检查、direct 完成事件、修复路径等。相关测试合并运行结果：339 passed，18 subtests passed；364 条现存 `datetime.utcnow()` 弃用告警。没有在拼多多页面重新上传或提交。

另将旧任务的 `plan.0002.json` 中 `sourcePlan` 只读地用新编译器重编译：无计划错误，两个 `filledValue` 非空规则均带 `confirmed_absent` 条件许可。用该新合同验证旧工件仍为 `failed`，价格/库存两行的 `declarationAccepted=false`、`outcome=None`，说明协议许可修复没有把缺少有效证据的业务行自动算作完成。旧 `task_plan.json` 是已编译的历史合同，直接重检它仍会沿用旧规则；需要新审批或显式计划迁移才能让既有任务使用新编译结果。
